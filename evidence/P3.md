# P3 — Legacy backends behind adapters

**Goal (order §5 P3):** `legacy-pixel` and `legacy-uia` behind the kernel, behaviour
equivalent (dryRun / verify / human pause / refusal reasons), and the stroke toy's
drawing path kept out of production (it is now in-repo, see P4); dual-run the old
engine as the oracle.

## Adapters

| Adapter | Reuses | Owns nothing |
|---|---|---|
| `backends/legacy-pixel.js` | `dsh-click-matrix`: `__createRuntime` + `__buildToolDefinitions`, so the real helper, lattice snapping, window deny list, coordinate resolution, dryRun and verify paths run unchanged | authorization (kernel), audit (forwarded), human pause (kernel) |
| `backends/legacy-uia.js` | `dsh-x2`: `src/win32.js` (SendInput / SetCursorPos / BitBlt / window enumeration / key & text injection), `src/uia.js` (UIA PowerShell bridge), `src/capture.js` (PNG + dedupe + hash) | the same three |
| `backends/toy-draw.js` | the Win32 primitives above, for one bounded preset stroke | every production capability: it exists only for `stroke_toy` (see P4 / D3) |

How the kernel avoids double authorization: after the kernel has asked the human, it
opens the legacy pixel gate for exactly one action
(`state.gate.openArm({clicks: 1, source: 'dexter-gate'})`), so the engine's request
path is satisfied and never prompts a second time.

## Dual-run (A11)

```
node tools/dual-run.mjs --json baseline/local/dual-run.json
```

20 scenarios, both sides run against the real desktop (the old pixel engine
constructed exactly as the installed bundle constructs it). Outcome classes are
compared, never text.

**Result: 19/20 identical outcome classes** (latest artifact:
`baseline/local/dual-run.json`; an earlier run on a quieter desktop produced 20/20 —
the difference is only whether the old engine happened to be suspended by a real human
at that moment, and both cases pass A11's ≥19/20).

Both sides ran with the human pause OFF, because whoever is sitting at the keyboard
would otherwise modulate every write; the pause has its own live evidence (A9). This
run measures injection and refusal equivalence.

| Scenario group | n | Result |
|---|---|---|
| reads: info / list / read / text / capture / zoom / locate / wait / wait_window ×2 | 10 | 10/10 same |
| dryRun click, dryRun click with a mismatched `expect` | 2 | 2/2 same (`previewed/dryRun`) |
| real cursor moves (5) | 5 | 5/5 same |
| validation (empty text, unknown read action) | 2 | 2/2 same |
| **write with no authorization at all** | 1 | **differs — deliberate (D7)** |

### The one deliberate rule difference (D7), measured without injecting

The dual-run compares *outcome classes*, so "both refuse" hides a real difference in
the rule. `tools/rule-probe.mjs` asks both layers the same question — "may this caller
inject with no grant and no approval service?":

```
old   move : allowed=true   (code 'allowed')
old   click: allowed=false  (code 'approval-unavailable')
new   move : allowed=false  (approval 'none')
new   click: allowed=false  (approval 'none')
differsOnMoveOnly: true
```

The old engine's `checkMove()` (`engines/pixel/lib/access.js:584`) only checks
mode/paused/suspended/rate-limit — cursor movement was never gated. dsh-dexter gates
`move` like every other write capability (order 4.2 lists it as a write, 4.3 requires
one gate for all writes). Inside a session a hover costs one action from the budget;
with no session it asks once.

This is a deliberate strengthening, not a regression. A caller that only needs to
hover can use `dryRun` or a session (`/dexter arm 15m 100`, `Ctrl+Alt+F12`).
